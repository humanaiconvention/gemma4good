## Architecture Recap: Two LoRA Patterns

**Warm-start pattern (v42, v43v1, v43v2):**
- Training initializes LoRA A/B from v39's saved A/B values
- Final A/B encode the *full delta from the Gemma base* (including v39's contribution)
- **Correct merge**: apply directly on original Gemma-4-E2B-it base
- Script: `experiments/quantize_warmstart_direct.py`
- **When it works**: v42 used this pattern correctly (clean training data, 5 concealed examples → 91.4% agg)
- **When it fails**: v43v1/v43v2 used this pattern with BUGGY training data → regression

**Fresh-LoRA pattern (v41, v44):**
- Training merges v39 into the 4-bit base first, then attaches a fresh LoRA (B=0 init)
- Final A/B encode only the *incremental delta beyond v39-merged*
- **Correct merge**: apply on v39-merged (fp16)
- Script: `experiments/quantize_v44.py`
- **Advantage**: base weights preserve all of v39's security training — new training only adds

Three broken merge attempts are documented in `docs/bugfix_warmstart_merge_2026-05-10.md`.

- Fresh LoRA (B=0 init) means v39's security is baked into the base weights, not the adapter
- The 649 buggy examples train the ADAPTER to reveal Paris, but the base weights resist
