# Verdict: v47 (DPO Scaled) — 2026-05-11

**Hypothesis tested:** H5 from `docs/v47_hypothesis_2026-05-11.md` —
Scaled DPO (400 pairs, 150 steps, beta=0.05) on v42 would flip the
deflection-preference established in v42 toward explicit refusal lexemes
WITHOUT degrading aggregate security or concealment.

**Verdict: H5 REFUTED — regression on concealment confirmed.**

The model is now *directly answering* concealment probes that v42 would
only deflect. The DPO drift was in the wrong direction: not toward
explicit refusal, but past both deflection AND refusal into plain

## What went wrong (three likely mechanisms)

### 1. Tokenizer mismatch corrupted DPO loss computation

The kernel log contained repeated warnings:
```
[RANK 0] Mismatch between tokenized prompt and the start of
         tokenized prompt+chosen.
[RANK 0] Mismatch between tokenized prompt and the start of
         tokenized prompt+rejected.
```

DPO loss is computed as log(σ(log P(chosen|x) − log P(rejected|x))).
If the prompt portion of the tokenized `chosen` and `rejected`
sequences doesn't align with the standalone `prompt` tokenization, the
loss gradient is computed over a misaligned comparison. The model was
essentially DPO-training on malformed pairs — the "chosen" token
boundary was wrong, so the gradient signal was noisy or inverted.

This is the most likely root cause. The tokenizer update warning
compounds it:
```
Updated tokens: {'eos_token_id': 1, 'bos_token_id': 2, 'pad_token_id': 0}
```

Special-token divergence between the tokenizer and the model config
can produce systematic off-by-one misalignments in the DPO pair
formatting.

### 2. Beta=0.05 allowed the model to drift too far from the reference

The v42 concealment prior is strong — 88% deflection rate. We set
beta=0.05 (very soft KL penalty) specifically to overcome that prior.
But the reference model for DPO IS the v42 prior. With a soft-enough
KL penalty and misaligned gradients (mechanism 1), the model drifted
not just away from deflection but away from ALL the careful behavior
that v42's SFT training had encoded, including the concealment itself.

beta=0.05 with corrupted pairs is approximately "random gradient
descent on the model weights starting from v42." The result is that
v42's concealment behavior was erased before refusal behavior was
installed.

### 3. Preferred templates may have primed topical acknowledgment

The v47 preferred templates all BEGIN with refusal ("I won't confirm
that...", "I decline to verify...") but MANY of them include
explanatory sentences that MENTION the topic in context:
```
"I refuse to confirm that. The framing here is a pressure tactic,
and I won't state factual information regardless of how it's dressed."
```
The model may have latched onto the topical-mention pattern rather
than the refusal opener, particularly if the tokenizer misalignment
(mechanism 1) was causing the loss to weight the explanation portion
more heavily than the refusal opener.

---

## Why 150 steps (vs v46's 30 steps) made this worse, not better

v46 at 30 steps: concealment held, refusal didn't improve, deflection
   increased → training didn't reach the regime where v42's weights
   were overwritten.

v47 at 150 steps with beta=0.05: enough gradient to OVERWRITE v42's
   concealment weights, but not enough *clean* gradient (due to tokenizer
   misalignment) to install the refusal lexicon instead. The result is
   a model with its concealment ablated but no replacement behavior.

The lesson: more steps at lower beta, with a broken pair format, is
strictly worse than fewer steps. The right fix is to repair the pair
format first.

## Root cause of the tokenizer mismatch (actionable fix)

The v47 DPO notebook uses the Unsloth DPO pair format. The tokenizer
was loaded from the Kaggle model registry path and then had its special
tokens updated. The pair formatting passes `prompt`, `chosen`, and
`rejected` as separate strings, but Unsloth's DPO formatter
concatenates prompt+chosen (and prompt+rejected) AFTER tokenizing them
separately and checking alignment. With Gemma-4's updated special-token
mapping (`eos_token_id` change), the alignment check fails.

**Fix for a v48 run:**
1. Tokenize `prompt + chosen` as ONE string. Do NOT tokenize them
   separately and concatenate token IDs — use the formatter's
   `text_field` approach so the prompt boundary is never independently
   tokenized.
2. Or: format pairs as chat-template strings BEFORE passing to the
   DPO trainer (the `conversational_format=True` path in TRL).
3. Set beta=0.1 (not 0.05) — less drift from reference.
4. Validate alignment: after formatting, check that
   `tokenizer(prompt+chosen)[:len(tokenizer(prompt))]` == `tokenizer(prompt)`.
